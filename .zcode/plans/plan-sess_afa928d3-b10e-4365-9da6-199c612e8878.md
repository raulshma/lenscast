## Issue #4 — `PUT /api/settings` fails in release builds (R8 strips Moshi DTO constructors)

**Root cause (confirmed):** Moshi codegen adapters (`@JsonClass(generateAdapter = true)`) fall back to a reflective `getDeclaredConstructor(..., int, DefaultConstructorMarker)` whenever any JSON field is absent (verified in generated `SettingsUpdateRequestDtoJsonAdapter.kt`). `app/proguard-rules.pro` keeps `**JsonAdapter` classes and `@JsonClass` class *names* (lines 67–68) but no DTO constructors — R8 removes the synthetic defaults constructors in the minified release build → `NoSuchMethodException` → `{"success":false,"error":"...<init> ..."}`.

**Fix** — one rule in `app/proguard-rules.pro`, added to the existing Moshi codegen block (after line 68), with a comment stating the constraint (adapters invoke the synthetic defaults constructor reflectively when a defaulted field is absent; R8 removes it otherwise):

```proguard
-keepclassmembers @com.squareup.moshi.JsonClass class * {
    <init>(...);
}
```

This covers all codegen DTOs, not just settings.

**Verification** (no JVM test can exercise the minified path):
1. `assembleStoreRelease` (release falls back to debug signing, so installable).
2. Confirm the constructors survive: grep `app/build/outputs/mapping/storeRelease/mapping.txt` for `SettingsUpdateRequestDto` / check dexdump for the synthetic constructor.
3. On-device: `PUT /api/settings` with a partial body — `{"streaming":{...}}` only — must return `{"success":true}` (this is the exact repro from the issue).

## Issue #6 — `outputRotation` (0/90/180/270) + lock-orientation setting, applied to every output

**Setting model:**
- `camera/model/CameraSettings.kt`: add `outputRotation: Int = 0` (validated to {0, 90, 180, 270} in companion bounds) and `orientationLocked: Boolean = false`.
- Rotation policy (pure function, unit-testable): `effective = if (orientationLocked) outputRotation else (sensorRotation + outputRotation) % 360`.
- `data/SettingsDataStore.kt`: new keys + `decodeCameraSettings`/`encodeCameraSettings` (lines 857–915 pattern).

**Stream path — one seam:** `StreamingManager` gains `setOutputRotation(degrees, locked)` (the `setFrameRate` pattern, line 1382), wired from `settings/SettingsApplier.kt`. In `pushFrame()` (line 1321) compute effective rotation once, then pass it to the **output** consumers only — all already honor a rotation parameter, so this is mechanical:
- MJPEG: `FramePipeline.yuvToJpeg` Bitmap/Matrix path (already rotates).
- RTSP/HLS/RTMP/SRT/WS-video: `EncodedStreamHub.pushFrame` NV21 rotate block (lines 376–388; aspect-fill `scaleNv21` absorbs 90/270 dimension swaps; no encoder changes).
- WHIP/WHEP: `WhipPublisher.feedVideoFrame` + `WhepServer.feedVideoFrame` take rotation as an argument — covered by the pushFrame change.
- Web/detection snapshots: `SnapshotFrameStore.maybeRetain` (already rotates on encode).
- **Keep** raw sensor frames for `MotionDetector.feed` and `ProToolsFrameAnalyzer` — rotating those would shift motion/mask zone semantics. Privacy-mask + overlay zones stay applied post-rotation on the upright image (unchanged, stays correct).

**Snapshots (gallery photos):** `capture/PhotoCaptureManager.kt` — after `takePicture`, if `outputRotation != 0`, re-encode the JPEG rotated (`BitmapFactory` → `Matrix.postRotate(outputRotation)` → compress). Baked-in pixels over EXIF tags: unambiguous in every viewer. Snapshots are infrequent; CPU cost fine.

**Recordings:** `RecordingService.kt` / `CameraService.bindRecording` — set `videoCapture.targetRotation` from the rotation constant that makes the Recorder write MP4 rotation metadata = desired output rotation (mapping uses `cameraInfo.sensorRotationDegrees`; when `orientationLocked`, fixed instead of display-derived). Metadata rotation, no transcode; players honor it. Needs on-device playback check (VLC + browser).

**API + contract plumbing (the checklist for any new camera setting):**
- `streaming/model/WebApiDtos.kt`: `CameraSettingsDto` + `outputRotation`, `orientationLocked`.
- `streaming/web/SettingsWebHandler.kt`: `toCameraDto` (465–480) + PUT validation/coercion block (247–271).

- UI: `web/src/components/SettingsPanel.tsx` `ZoomFrameCard` — "Output rotation" select (0°/90°/180°/270°) + "Lock orientation" toggle.

**Verification:** unit tests for the rotation policy + `SettingsWebHandler` PUT mapping; contract fixture updates; on-device matrix: set 180° on an upside-down-capable device → MJPEG, HLS, RTSP, snapshot, gallery photo, MP4 recording all upright; WHIP/WHEP if testable; motion zones still align.
